1. Executive Summary & Problem Statement

1.1 Problem Statement: In university environments, students often struggle with specific difficult courses or topics (such as Calculus in MTH 102 or Data Structures in CSC 201). Simultaneously, talented peer students who have mastered these subjects are willing to assist their peers but lack a structured, safe, and organized campus platform to schedule sessions, share verified study materials, or track tutorial attendance.

1.2 The Solution: StudyConnect bridges this academic gap through a dual-role peer-to-peer system. A student does not have to be solely a "tutor" or a "learner". They can offer tutoring in subjects they excel at while simultaneously receiving academic support in subjects they find challenging.

1.3 Core Pillars:

  • Dual-Role Onboarding: Seamless registration with university email, department, level, and course selections.
  • 1-on-1 & Group Tutoring Sessions: Scheduled physical meetups at verified campus locations or online Google Meet calls.
  • Course & Topic Search: Instant catalog search connecting students by specific curriculum topics.
  • Study Partner Matching & Reshuffle: Automatic pairing of classmates with mutual study goals and schedule availability.
  • Attendance & Accountability: Session confirmation and tracking to foster consistent study habits.
  • Academic Material Sharing: Upload and download past examination questions, lecture notes, and study summaries.
  • Trust & Safety: University email verification via OTP, 1-to-5 star ratings, testimonials, and conduct reporting.

2. Architectural Pattern: The 5-Layer Backend Flow

To ensure every team member understands how a request flows through the backend (and can clearly explain it during project defense), the application follows a strict 5-layer separation of concerns:

[ CLIENT (Web Browser / Mobile App) ] │ (HTTP Request with JSON payload & optional Bearer JWT) ▼ [ 1. CONTROLLER LAYER ] (src/modules/*/controllers/*.controller.ts) • Listens on HTTP endpoints (GET, POST, PATCH, DELETE) • Enforces DTO validation via class-validator (strips invalid fields) • Applies authentication guards (@UseGuards(JwtAuthGuard)) │ ▼ [ 2. SERVICE LAYER ] (src/modules/*/services/*.service.ts) • Houses all business logic and calculations • Hashes passwords with bcryptjs • Triggers OTP generation and Resend email dispatches • Calculates rating averages and attendance counters │ ▼ [ 3. REPOSITORY LAYER ] (src/modules/*/repositories/*.repository.ts) • Abstraction for database queries • Isolates complex SQL / query builders from business logic │ ▼ [ 4. TYPEORM ENTITY / SCHEMA LAYER ] (src/modules/*/entities/*.entity.ts) • TypeScript classes decorated with @Entity(), @Column(), @ManyToOne() • Represents the strict structure of our tables in code │ ▼ [ 5. POSTGRESQL DATABASE ] (Hosted on Render.com) • Permanent, relational ACID-compliant data storage

Why This 5-Layer Pattern Matters:

  • Controllers never write SQL. They only accept requests and return responses.
  • Services never know about HTTP headers or status codes. They focus strictly on business logic.
  • TypeORM Entities define the schema in TypeScript, preventing discrepancies between code and database.
  • PostgreSQL guarantees relational integrity using foreign keys and cascading rules.

3. Technology Choices & Architectural Justification

Every technology in the StudyConnect stack was selected for reliability, team collaboration speed, and academic defensibility:

Technology What It Is Why It Was Picked Over Alternatives Real-Time Impact
NestJS (TypeScript) Enterprise Node.js web framework. Plain Express gives zero structure, causing displaced files in multi-developer teams. NestJS enforces modular architecture. Each module (Auth, Users, Courses, Tutoring) has its own self-contained folder.
PostgreSQL Relational SQL database. Selected over MongoDB because students, courses, bookings, and reviews are strictly relational. Foreign keys prevent orphan records. 100% data integrity; impossible to book a session for a non-existent student or course.
TypeORM Object-Relational Mapper (ORM). Translates TypeScript entity classes directly into PostgreSQL tables, eliminating manual SQL string errors. Automatic schema synchronization in development; clean migrations for production.
Redis In-memory data structure store. Storing temporary 10-minute OTP codes and rate-limiting counters in PostgreSQL wastes disk I/O. Redis keeps them in RAM. Sub-millisecond (< 1ms) response times for rate-limiting checks and OTP verification.
Resend Modern email delivery API. Provides 3,000 free emails/month, requires zero server setup, and sends transactional verification emails via a 3-line SDK call. Instant OTP code delivery to student inboxes without maintenance headaches.
Bcryptjs Password hashing library. Pure JavaScript implementation. Native C++ bcrypt fails to compile on many Windows student machines. Bcryptjs works everywhere. Secure, salt-based one-way password hashing across all operating systems.
Swagger (OpenAPI) Interactive API documentation. Auto-generates a live web playground at /docs from TypeScript code, eliminating manual Postman exports. Beginners and frontend engineers can test endpoints directly in their web browser.
Render.com Cloud hosting platform. Free managed PostgreSQL database and Node.js web services with direct Git integration. Zero-cost production deployment with automatic redeployment on git push.

4. Detailed Feature Specifications & Technical Realization

Feature 1: Student Authentication & Resend OTP Verification

Functional Experience: Students register with their email, password, full name, department, level, and pick their role (TUTOR, LEARNER, or BOTH). An unverified account is created and a 6-digit OTP code (valid for 10 minutes) is sent to their email via Resend. A 60-second cooldown prevents spamming. Once verified, a JWT token is issued.

Technical Realization:

  • POST /api/v1/auth/register ➔ Validates body via RegisterDto, hashes password with bcryptjs (cost 10), saves User with isVerified: false.
  • POST /api/v1/auth/verify-otp ➔ Compares submitted OTP against Redis key otp:{email}. On match, sets isVerified: true and returns JWT Bearer token.
  • POST /api/v1/auth/resend-otp ➔ Rate-limited to 1 request per 60s per IP. Throws 429 Too Many Requests if spammed.
  • POST /api/v1/auth/login ➔ Validates credentials via LocalStrategy, returns access token.

Feature 2: Student Profiles & Dual-Role Attributes

Functional Experience: Students view and update their profile. They can list course codes they are proficient in teaching (e.g. ["CSC201", "MTH101"]) and course codes where they need tutoring (e.g. ["PHY102"]), plus bio and contact details.

Technical Realization:

  • GET /api/v1/users/profile/me ➔ Reads authenticated user from JWT payload via @CurrentUser() decorator.
  • PATCH /api/v1/users/profile/me ➔ Updates coursesToTeach, coursesNeedingHelp, bio, and avatarUrl.
  • GET /api/v1/users/:id ➔ Returns public profile with average rating, review count, and session totals.

Feature 3: Course Catalog & Topic-Based Search

Functional Experience: A student searching "Integration" or "MTH 102" receives matching courses, curriculum topics, and available student tutors.

Technical Realization:

  • GET /api/v1/courses ➔ Lists registered courses with curriculum topic breakdown.
  • GET /api/v1/courses/search?q=Integration ➔ Queries courses and topics using PostgreSQL case-insensitive ILIKE matching.
  • Standard SQL Counting: Returns real-time counts of available tutors and learners seeking help per course using indexed SQL aggregation.

Feature 4: 1-on-1 and Group Tutoring Sessions & Campus Meetups

Functional Experience: Students arrange tutorial sessions by selecting date, time, duration, session type (1-on-1 or group max 5), and a meetup venue (e.g., "Main Library Room 4" or a Google Meet URL).

Technical Realization:

  • POST /api/v1/tutoring/sessions ➔ Creates session with initial status SCHEDULED. Links tutor and learner IDs.
  • GET /api/v1/tutoring/my-sessions ➔ Returns upcoming and past sessions for the logged-in student.
  • PATCH /api/v1/tutoring/sessions/:id/cancel ➔ Cancels session with reason logging.

Feature 5: Study Partner Matching & Reshuffling

Functional Experience: Students find a reading partner based on common courses and study schedules. If a partner becomes inactive or unavailable, the student can click "Reshuffle" to be paired with another peer.

Technical Realization:

  • POST /api/v1/partners/match ➔ Queries learners sharing the same course codes in coursesNeedingHelp.
  • POST /api/v1/partners/:matchId/reshuffle ➔ Marks existing pairing RESHUFFLED and queries the next best available partner.

Feature 6: Attendance Tracking & Verification

Functional Experience: When a tutoring session concludes, the tutor marks attendance. The learner's attended count increments and the session is marked completed.

Technical Realization:

  • POST /api/v1/attendance/:sessionId/verify ➔ Tutor marks attendance. Sets attended: true in session_participants.
  • Increments totalSessionsGiven on the tutor profile and totalSessionsAttended on the learner profile inside a database transaction.

Feature 7: Tutor Ratings & Reviews

Functional Experience: Learners rate their tutor from 1 to 5 stars and write a testimonial. The tutor's public rating recalculates automatically.

Technical Realization:

  • POST /api/v1/reviews ➔ Stores review with rating (1–5) and comment. Only allowed if session attendance was verified.
  • Updates tutor's running average rating = SUM(stars) / reviewCount.

Feature 8: Academic Material Sharing Hub

Functional Experience: Students upload and download PDF lecture notes, past questions, and formula summaries tagged by course code. Max size 10MB.

Technical Realization:

  • POST /api/v1/materials/upload ➔ Validates MIME types (strictly PDF, PNG, JPG, DOCX). Stores files securely in uploads/materials.
  • GET /api/v1/materials?courseCode=MTH102 ➔ Lists materials for download with download counters.

Feature 9: Student Safety & Conduct Reporting

Functional Experience: Students can report inappropriate behavior or missed meetups with a single click.

Technical Realization:

  • POST /api/v1/reports ➔ Creates moderation report with reporter ID, reported ID, reason, and description.

5. Database Schema & Data Dictionary

All database tables inherit from BaseEntity, providing id (UUID primary key), createdAt, and updatedAt.

Table Name Primary & Foreign Keys Key Attributes Description
users id (PK, UUID) email, password, firstName, lastName, role, department, level, coursesToTeach, coursesNeedingHelp, rating, isVerified Stores all student credentials, profile details, and tutoring preferences.
courses id (PK, UUID) code (e.g. MTH102), title, department, level Official university course catalog.
topics id (PK), courseId (FK) title (e.g. Integration), difficulty Specific topics taught under each course.
tutoring_sessions id (PK), tutorId (FK), courseId (FK) sessionType, locationVenue, meetingUrl, scheduledAt, durationMinutes, status Booked 1-on-1 and group tutorial sessions.
session_participants id (PK), sessionId (FK), learnerId (FK) attended (Boolean), feedback Tracks learners enrolled in and attending a tutorial.
study_partner_matches id (PK), studentAId (FK), studentBId (FK) courseId (FK), status (ACTIVE / RESHUFFLED) Matched peer reading and study partners.
materials id (PK), uploaderId (FK), courseId (FK) title, fileUrl, fileType (PAST_QUESTION, NOTES), downloadsCount Shared study resources, notes, and previous exams.
reviews id (PK), sessionId (FK), tutorId (FK) rating (1–5), testimonial Student feedback and tutor reputation records.
reports id (PK), reporterId (FK), reportedUserId (FK) reason, description, status (PENDING, RESOLVED) Campus safety and moderation complaints.

6. Security, Rate Limiting & Response Architecture

6.1 Uniform API Response Envelope

All successful HTTP responses are wrapped automatically by TransformInterceptor:

{ "success": true, "statusCode": 200, "message": "Operation successful", "data": { ... }, "timestamp": "2026-10-22T04:30:00.000Z" }

6.2 Centralized Exception Handling

All errors (validation failures, 404s, 401s, 429s) are formatted uniformly by AllExceptionsFilter:

{ "success": false, "statusCode": 400, "message": "Password must be at least 6 characters long", "path": "/api/v1/auth/register", "timestamp": "2026-10-22T04:30:00.000Z" }

6.3 Rate Limiting Rules (Throttler + Redis)

  • OTP Request Burst Limit: Max 1 request per 60 seconds per IP (prevents spamming student inboxes).
  • Login Brute-Force Limit: Max 5 attempts per 15 minutes per IP.
  • General API Limit: Max 100 requests per minute per IP.

7. DevOps & Render.com Cloud Deployment Guide

To deploy the StudyConnect backend live for evaluation, follow these exact steps on Render.com:

  1. Create PostgreSQL Database on Render:
    • Log in to render.com ➔ Click New + ➔ PostgreSQL.
    • Name: study-connect-db ➔ Select Free Plan.
    • Copy the Internal Database URL (or Host, Port, User, Password).
  2. Create Web Service on Render:
    • Click New + ➔ Web Service ➔ Connect your GitHub repository.
    • Runtime: Node.
    • Build Command: npm install && npm run build
    • Start Command: npm run start:prod
  3. Configure Environment Variables in Render Dashboard:
    • NODE_ENV = production
    • PORT = 3000
    • DB_HOST, DB_PORT, DB_USERNAME, DB_PASSWORD, DB_DATABASE (From Render Postgres)
    • JWT_SECRET = (Secure random 64-char string)
    • RESEND_API_KEY = re_... (From Resend.com dashboard)
  4. Verify Deployment:
    • Visit https://your-service.onrender.com/api/v1/health ➔ Returns {"status": "healthy"}.
    • Visit https://your-service.onrender.com/docs ➔ Interactive Swagger Documentation is live!
